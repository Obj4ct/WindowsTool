## 一、现状诊断

### 1.1 当前的检测逻辑

```
点击「自动检测并修复」
    ↓
ping www.baidu.com                         ← 唯一探测点
    ↓
  找不到主机 ──→ ping www.baidu.com（第二次）
                      ↓
                  nslookup baidu.com
                      ↓
                  DNS 失败 ──→ fixDNS.bat → 问用户"能上网了吗"
                      ↓
                  通过 → "网络连接正常"
```

### 1.2 实测发现的问题

| #   | 问题                          | 实测证据                                                                                                                                     | 严重度  |
| --- | --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ---- |
| 1   | **单点探测，结论必然片面**             | 本机 5 个网卡同时 Up（以太网 / WLAN / VMware VMnet1 / VMnet8 / xray_tun）。`Test-NetConnection` 实测流量实际走 **`xray_tun`**，而 ping 走的是同一路径——但用户可能以为在用 WLAN | 🔴 高 |
| 2   | **DNS 检测靠解析本地化文本**          | `netcheck.h` 里硬编码 `"找不到主机"` / `"Non-existent domain"` 等 7 个关键词。换个系统语言就失效                                                                 | 🔴 高 |
| 3   | **DNS 检测绕过真实路径**            | `nslookup` 直接问 DNS 服务器，而浏览器实际走的是「代理 → VPN 隧道 → DNS」。三者可能给出完全不同的答案                                                                        | 🟠 中 |
| 4   | **代理因素完全未考虑**               | 本机 `ProxyEnable=1, ProxyServer=127.0.0.1:10808`。作者自己在提示语里写过"确保在电脑设置中关闭了代理"，但程序**从不检测代理**                                                 | 🟠 中 |
| 5   | **`fixDNS.bat` 在中文系统上静默失效** | `netsh interface show interface` 中文系统输出表头是「管理员状态/状态/类型/接口名称」，脚本里的 `findstr /c:"Admin State"` **永远匹配不到**                                  | 🔴 高 |
| 6   | **`fixDNS.bat` 会破坏用户配置**    | 它把**所有**网卡重置为 DHCP：会抹掉手工设的静态 IP；会把 VPN 虚拟网卡（xray_tun / Wintun）也去设 DHCP——这类适配器压根不适用                                                       | 🔴 高 |
| 7   | **"修复"无法验证**                | 修复后靠弹窗问用户"是否可以上网"，是主观判断，且没有复检                                                                                                            | 🟡 中 |
| 8   | **结果只有纯文本**                 | 诊断结论混在日志流里，看不出"哪一层出问题"                                                                                                                   | 🟡 中 |

### 1.3 一个典型的误判场景

> 用户接了 VPN（或公司配了代理），DNS 走的是代理的 DNS。
> 本机 `nslookup` 查的是网卡上配的 `192.168.3.1`（WLAN 的 DNS）→ 成功 → 程序说"网络正常"。
> 但浏览器访问走代理，代理挂了 → 用户实际上打不开网页。
> **程序给的是假绿灯。**

### 1.4 2026-10-30 已落地的修复（本轮）

| 原问题                                  | 处置                                                                   |
| ------------------------------------ | -------------------------------------------------------------------- |
| #5 `fixDNS.bat` 依赖英文表头 `Admin State` | 改用 PowerShell `Get-NetRoute` + `Get-NetAdapter` 选取目标网卡，不再解析 netsh 文本 |
| #6 把所有网卡重置为 DHCP                     | 只处理**承载默认路由的物理网卡**；静态 IP 不改写，VPN / VMware / Wintun 等虚拟网卡跳过           |
| 提权后父进程立即返回，靠固定 5 秒猜修复是否完成            | 提权改为 `Start-Process -Wait -PassThru`，程序以 `finished` 信号为准             |
| 自动检测的 `QTimer` 可能覆盖用户新点的任务           | 引入 `m_flow` 流程世代号，旧流程的定时器自动放弃                                        |
| 修复前没有配置备份                            | 每次刷新前把 `ipconfig /all` 备份到 `%ProgramData%\WindowsTool\`              |
| 脚本末尾 `pause` 让任务一直挂起                 | cleaner / winsockReset 去掉 `pause`，任务能正常收尾并回写完成日志                     |

## 二、目标

1. **分层定位**：明确回答"断在哪一层"，而不是"网络有问题"
2. **结论可靠**：不依赖系统语言、不依赖某个外部命令的输出格式
3. **修复精准**：按诊断结论选择动作，不做全局破坏性操作
4. **结果可读**：结构化展示 + 可复制分享
5. **可新增依赖**：可引入第三方开源库（准入条件见 15.8：MIT/Apache/BSD 等宽松许可优先，须登记许可证与体积）

## 三、方案架构

### 3.1 总体结构

```
┌─────────────────────────────────────────────────────────┐
│  MainWindow                                               │
│  ┌───────────────────┐  ┌─────────────────────────────┐ │
│  │ NetDiag（新增）    │  │ ProcessRunner（现有）        │ │
│  │ 分层探测编排       │  │ 跑 bat / PowerShell 脚本     │ │
│  └─────────┬─────────┘  └──────────────┬──────────────┘ │
│            │                           │                │
│   ┌────────┴────────┐         ┌────────┴────────┐       │
│   │ QNetworkAccess   │         │ netdiag.ps1     │       │
│   │ Manager（Qt 内）  │         │ 本机状态快照     │       │
│   │ · DNS 探测        │         │ → JSON          │       │
│   │ · HTTP 端到端     │         │ （网卡/路由/代理）│       │
│   │ · 原始 UDP DNS   │         └─────────────────┘       │
│   └──────────────────┘                                    │
└─────────────────────────────────────────────────────────┘
```

### 3.2 关键决策：PowerShell 只做「读状态」，探测全部在 Qt 内

| 事项                             | 放在哪                          | 理由                                                              |
| ------------------------------ | ---------------------------- | --------------------------------------------------------------- |
| 网卡 / IP / 网关 / DNS / 默认路由 / 代理 | PowerShell（输出 JSON）          | 这是 OS 内部状态，Qt 没有 API 能拿；`Get-NetAdapter` 等 cmdlet **输出与系统语言无关** |
| DNS 能否解析                       | Qt 内自己发 UDP DNS 查询           | 绕开 `nslookup`/`Resolve-DnsName` 的文本输出，100% 可控、可测延迟、可指定服务器       |
| HTTP 端到端能否访问                   | Qt 内 `QNetworkAccessManager` | 直接用浏览器的网络栈（含系统代理），最接近用户真实体验                                     |

**为什么不全程用 PowerShell？** 每起一个 powershell 进程约 300–800ms，多项检测累积到 3–5 秒，界面明显卡顿。折中：**一次调用拿全部本机状态（JSON），其余在 Qt 内快速完成**。

## 四、分层诊断模型（核心）

从下往上逐层检查，**报告第一个失败的层**。

```
┌──────────────────────────────────────────────────────────┐
│ L7 应用层   浏览器实际访问（走系统代理 + WinINET）           │  ← 最贴近用户体验
├──────────────────────────────────────────────────────────┤
│ L6 代理层   系统代理 / PAC / WinHTTP 代理 是否存在且可达      │  ← 常见坑
├──────────────────────────────────────────────────────────┤
│ L5 HTTP 层   HTTPS 请求能否拿到响应（含 TLS 握手）           │
├──────────────────────────────────────────────────────────┤
│ L4 TCP 层    到目标 IP:443 能否建立连接                      │  ← 防火墙/墙在这里
├──────────────────────────────────────────────────────────┤
│ L3 DNS 层    域名能否解析成 IP                              │  ← 最高频故障点
├──────────────────────────────────────────────────────────┤
│ L2 路由层    到目标 IP 有无路由，实际走哪个网卡                │
├──────────────────────────────────────────────────────────┤
│ L1 链路层    目标网卡是否 Up、有无有效 IP、有无默认网关        │  ← 拔网线/无WiFi
└──────────────────────────────────────────────────────────┘
```

### 4.1 各层判定与输出

| 层   | 检查方式                 | 失败结论              | 建议动作             |
| --- | -------------------- | ----------------- | ---------------- |
| L1  | JSON 里网卡状态 / IP / 网关 | `未连接` / `IP 配置异常` | 检查网线、WiFi、DHCP   |
| L2  | 默认路由 + 路由表匹配目标 IP    | `路由缺失`            | 检查静态路由/VPN 路由    |
| L3  | 自发 UDP DNS 查询        | `DNS 解析失败`        | 换 DNS / 刷 DNS 缓存 |
| L4  | TCP connect          | `连接被阻断`           | 检查防火墙、代理软件       |
| L5  | HTTPS 请求             | `HTTP 异常`         | 检查证书、代理认证        |
| L6  | 代理注册表 + 连通性          | `代理不可用`           | 关闭/更换代理          |
| L7  | 用系统代理栈发请求            | `浏览器也无法访问`        | 综合判定             |

### 4.2 判定结果的数据结构

```cpp
enum class Layer { Link, Route, Dns, Tcp, Http, Proxy, App };

struct CheckItem {
    Layer      layer;
    QString    name;        // "DNS 解析"
    Status     status;      // Pass / Fail / Warn / Skip
    QString    detail;      // "223.5.5.5 响应 23ms"
    int        elapsedMs = -1;
};

struct DiagResult {
    QVector<CheckItem> items;
    Layer    firstFailed = Layer::App;   // 首个失败层
    QString  summary;                     // 一句话结论
    QString  suggestion;                  // 针对性建议
};
```

### 5.2.2 建议裁剪（待确认，未实施）

| 功能             | 建议                         | 理由                                                                                                                                                                                                                 |
| -------------- | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **垃圾清理**       | **保留入口**，但改为「打开系统临时文件清理面板」 | ① 收益极小：现代 Windows 的临时文件本就由系统按需清理 ② 代价高：需提权弹 UAC、弹黑窗口 ③ 有风险：自己写删除逻辑，一旦路径判断失误就是误删 ④ 已有更好的：Windows 自带「设置 → 系统 → 存储 → 临时文件」，覆盖面更全更安全。<br>**处置**：改成一行命令调起系统清理面板，用户在原生界面里勾选要删什么——我们只负责"打开入口"，不做删除动作（与 15.2「系统清理」模块定位一致）。 |
| **重置 WinSock** | **保留**，但明确标注代价             | 有真实场景（安全软件残留导致协议栈异常），无系统原生替代。但需重启才生效，必须在确认弹窗里说清楚。                                                                                                                                                                  |

### 5.2.3 弹窗文案规范化（已落地）

原实现的弹窗大量使用口语与情绪化表达（"疑问"、"别开玩笑"、"555，你开心就好了"），
在故障场景下会让用户觉得"这软件不靠谱"。规范化原则：

1. **标题 = 动作或结果**，不用情绪词 —— "刷新网络配置" 而非 "提示"
2. **正文 = 发生了什么 → 可能原因 → 建议动作**，三段式
3. **涉及系统改动必须前置警示** —— 说明影响范围、是否可逆、是否需要重启
4. **错误信息要具体** —— 指明缺哪个文件、完整路径，而非"找不到脚本文件"
5. **按钮文案描述动作** —— "可以正常访问" 而非 "可以"

对比示例：

| 场景            | 改前                                                             | 改后                                                                                            |
| ------------- | -------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 网络测试失败        | 标题「连接错误」<br>"网络连接出现问题，请检查是否连接网络（建议多检测几次）。如果已经连接，建议使用自动检测来检查问题" | 标题「连接超时」<br>"在规定时间内未收到目标主机的响应。\n\n可能原因：网络尚未连接、目标站点不可达，或存在代理/防火墙拦截。\n\n建议使用「自动检测并修复」定位具体故障环节。" |
| 修复后验证         | 标题「疑问」<br>"是否可以上网？"                                            | 标题「验证修复结果」<br>"网络配置已重置。请问当前是否可以正常访问网页？"                                                       |
| 修复仍失败         | 标题「开发者的话」<br>"软件为第一个版本，难免会有问题，请点击右上角「关于」来联系作者"                 | 标题「问题仍未解决」<br>"网络配置已重置，但访问仍不正常。\n\n可能是运营商侧故障、代理配置异常，或被安全软件拦截。\n\n可通过右上角「关于」获取联系方式以获取进一步支持。"   |
| 脚本缺失          | 标题「错误」<br>"找不到脚本文件 fixDNS.bat"                                 | 标题「缺少脚本文件」<br>"未找到所需的脚本文件 fixDNS.bat。\n\n请确认程序目录下的 bat 文件夹完整，或重新获取程序。"                        |
| 重置 WinSock 确认 | 标题「警告！」<br>一长串口语化描述                                            | 标题「重置 Winsock」<br>"此操作将重新初始化 Winsock 套接字目录…\n\n注意：重置后部分网络性能可能下降，且需要重启计算机才能完全生效。\n\n是否继续？"     |

> 注：文案规范化属于**表面改动**，真正让结论可信的是第五节的 F1 分层诊断——
> 专业文案的配得上"专业"二字，前提是诊断结论本身准确。

## 八、风险与权衡

| 风险                         | 影响                              | 应对                                                   |
| -------------------------- | ------------------------------- | ---------------------------------------------------- |
| **修复动作会改系统网络配置**           | 可能短暂断网，或影响静态 IP 用户              | 每次修改前**自动备份**原配置，提供回滚；只对**当前默认路由网卡**操作；物理网卡与虚拟网卡分开处理 |
| PowerShell 被策略禁用/缺失        | 本机状态拿不到                         | 降级到解析 `ipconfig /all`（有本地化风险），或直接跳过对应检查项并明示          |
| Win7 / 旧版 PowerShell       | `Get-NetAdapter` 等 cmdlet 可能不存在 | 脚本里做版本探测，不可用则用 `netsh` 兜底                            |
| 一次 PowerShell 调用 300–800ms | 界面短暂停顿                          | 异步执行 + 状态条提示；**所有本机状态一次拿完**，不做多次调用                   |
| UDP DNS 被企业防火墙拦截           | F2 测不出延迟                        | 探测超时≠DNS 故障，结合 L4/L5 结论综合判断，不单独下结论                   |
| 内置公共 DNS 属于"改动用户环境"        | 用户可能不希望                         | 默认**只测速不自动切换**；切换需显式点击 + 二次确认                        |
| 诊断逻辑复杂度上升                  | 维护成本                            | 分层模型用数据驱动（`CheckItem` 数组），每层独立可测；引擎不碰 UI             |

## 九、需要你拍板的几个点

> 已定事项：① 公共 DNS 切换——做，默认只测速，切换需二次确认；
> ② `netdiag.ps1` 放 `ps1/` 目录；③ 快捷键与截图功能已裁剪（见 5.2.1）。

1. **诊断结果要不要落盘保存历史？**
   涉及写文件到用户目录，可以只保留在内存里（本次退出即清）。

2. **网络页 UI 是"卡片列表"还是"保持现在的磁贴 + 展开详情"？**
   前者信息密度高、后者改动小。我倾向**磁贴保留、点击后展开分层结果面板**。

3. **「垃圾清理」要不要按建议改成「打开系统清理面板」？**
   见 5.2.2。改成调起 Windows 原生清理界面，我们不做删除动作——更安全也更省事。

4. **系统页留白要不要用 F15 填上？**
   ✅ 已解决：系统页已排入 6 个磁贴（垃圾清理 / 修复桌面图标 / 电脑体检 / 启动项管理 / 大文件扫描 / 磁盘健康），下方留白由结果卡片填充。

## 十四、不做什么（避免范围膨胀）

- ❌ 不做流量抓包 / Wireshark 替代品
- ❌ 不做网速测速的严谨实现（只做延迟/丢包近似）
- ❌ 不做路由表编辑器（危险且小众）
- ✅ 允许引入第三方开源库，但必须过 15.8 的依赖准入（许可证白名单 + 体积 + 维护状态）
- ❌ 不引入 GPL/AGPL 等传染性许可库、闭源硬件 SDK、带独立运行时的重依赖
- ❌ 不改动 `bat/` 现有脚本的 GBK 编码约定
- ❌ **不做与"修复常见电脑问题"无关的功能**（快捷键速查、截图教学等已裁剪）
- ❌ 不做快捷启动器（Flow Launcher）、窗口分屏（FancyZones）、分应用音量（EarTrumpet）——方向偏了
- ❌ 不做驱动安装/更新、系统镜像操作——高危且不可回滚（驱动只提供**只读清单**，见 15.3）
- ❌ 不做注册表清理——扫描规则难以证伪，误删代价远大于收益
- ❌ 不做广告推送、强制安装、后台常驻与"虚假性能提升百分比"（见 15.7）
- ❌ 不做账号体系与云同步——本地工具不需要

## 十五、产品定位与模块化路线（外部评审后补充）

> 来源：2026-10-30 外部评审意见（提出硬件监控、进程管理、驱动管理、软件中心、回滚中心等方向）。
> 采纳原则：**先判断"能不能安全地做"，再判断"值不值得做"**。
> 与本文第三、八、十四章约束冲突之处，在 15.3 中逐条裁定，不做无差别照单全收。

### 15.1 定位纠偏

不要把它做成"又一个垃圾清理软件"，而是 **Windows 系统维护与诊断工具箱**。

现有能力已覆盖五个方向，缺的不是按钮数量，而是**诊断深度与可回滚性**：

| 方向   | 现有功能             |
| ---- | ---------------- |
| 系统清理 | 垃圾清理、大文件扫描       |
| 网络维护 | 网络测试、网络修复、端口占用查询 |
| 系统修复 | 桌面图标白块修复         |
| 系统诊断 | 电脑体检、磁盘健康        |
| 系统管理 | 启动项管理            |

### 15.2 八大模块架构

| ---- | -------------- | ------------------------------------ |
| 概览   | —              | 电脑概览、健康评分、最近操作（P2）                   |
| 系统清理 | 垃圾清理、大文件扫描     | 重复文件、目录占用分析、浏览器缓存、卸载残留               |

### 15.3 功能取舍（Qt5 + 可引入第三方开源库的前提）

> 结论分三类：**做**（当前可行且低/中风险）、**缓**（可行但价值或风险不匹配，排后）、**不做**（违反第八章/第十四章约束）。

| 功能                       | 建议优先级  | 实现路径（系统组件优先，必要时引入开源库）                                                                                    | 裁定                                  |
| ------------------------ | ------ | --------------------------------------------------------------------------------------------------- | ----------------------------------- |
| 硬件信息快照（CPU/主板/内存/显卡/显示器） | P1     | WMI `Win32_Processor` / `Win32_VideoController` / `Win32_PhysicalMemory` → `ps1/hwinfo.ps1` 输出 JSON | 做                                   |
| 电池健康                     | P1     | `powercfg /batteryreport` 生成 HTML，Qt 解析关键字段或直接打开报告                                                  | 做（笔记本才显示入口）                         |
| CPU/内存实时曲线               | P2     | PDH `Get-Counter` 或 `ps1/monitor.ps1` 5s 采样；GPU 温度需 NVML/厂商 SDK（闭源，需单独评估）                     | 做 P2（CPU/内存/磁盘先行，GPU 传感器后置）      |
| 进程管理（列表 + 资源占用）          | P1     | `Get-Process` + WMI 命令行/父进程；结束进程走二次确认                                                               | 做（先只读列表）                            |
| 驱动清单（型号/版本/供应商/签名）       | P2     | `Win32_PnPSignedDriver`                                                                             | 做只读清单；安装/备份**不做**                   |
| SFC / DISM 系统文件修复        | P1     | 提权执行 `sfc /scannow`、`DISM /Online /Cleanup-Image /RestoreHealth`，实时回显进度                             | 做（长任务需进度条）                          |
| Windows 更新修复             | P2     | 停/启 wuauserv、清 SoftwareDistribution                                                                 | 缓（影响面大、失败难恢复）                       |
| 系统还原点                    | P2     | `Checkpoint-Computer` 需系统保护已开启                                                                      | 缓（先只读展示还原点状态）                       |
| 蓝屏分析                     | P2     | `dbghelp.dll`（系统自带）解析 minidump + 内置 BugCheck 代码字典；符号下载可选                                     | 做 P2（先列表 + 代码解释，完整栈回溯后置）            |
| 磁盘空间树形分析（treemap）        | P1     | 复用大文件扫描的遍历逻辑 + `QPainter` 自绘矩形树图                                                                    | 做                                   |
| 重复文件扫描                   | P1     | 已有计划（大小分组 → 哈希）                                                                                     | 做                                   |
| 软件卸载列表                   | P1     | 读 `Uninstall` 注册表键，调用卸载器需二次确认                                                                       | 做（先只读列表）                            |
| winget 软件中心              | P2     | 调 `winget search/install`，无 winget 隐藏入口                                                             | 缓（依赖网络与源）                           |
| 应用网络流量                   | P2     | `GetExtendedTcpTable` 取连接（系统 API）；按进程流量用 ETW `Microsoft-Windows-Kernel-Network`               | 做 P2（先做连接列表，流量统计后置）                    |
| 服务 / 计划任务管理              | P2     | `Get-Service` / `Get-ScheduledTask`                                                                 | 缓（只读可先做，写操作风险高）                     |
| 环境变量 / 右键菜单              | P2     | 注册表读写                                                                                               | 缓（仅查看）                              |
| 文件哈希 / 数字签名              | P1     | `QCryptographicHash`、`WinVerifyTrust`                                                               | 做                                   |
| 系统信息导出（HTML 报告）          | P1     | 复用 F9 报告导出                                                                                          | 做                                   |
| 统一回滚引擎                   | P1（底层） | 见 15.5                                                                                              | **优先做规范**，先于任何写功能                   |

### 15.5 统一可还原操作引擎（所有写操作的前置规范）

任何修改类功能（禁用启动项、切 DNS、改代理、结束进程之外的系统改动）都遵循同一生命周期：

1. **扫描检测** —— 读取当前状态，给出可执行的变更清单
2. **生成方案** —— 展示改什么、风险、预期效果，用户确认后执行
3. **备份原状** —— 注册表/配置文件/服务状态写入 `%ProgramData%\WindowsTool\backups\`，操作索引可用 JSON 或 SQLite（见 15.8）
4. **执行** —— 记录完整命令与输出日志
5. **验证** —— 复检确认生效，失败则自动提示回滚
6. **可回滚** —— 操作记录中一键恢复（仅限可逆项）

**边界必须明说**：已删除的文件、已清理的缓存、已安装的更新、已终止的进程**不可真正还原**。
界面上要标注"可恢复 / 部分可恢复 / 不可恢复"，不能承诺"所有操作一键撤销"。

### 15.6 三阶段路线（与当前进度对齐）

| 阶段       | 内容                                                      | 状态    |
| -------- | ------------------------------------------------------- | ----- |
| 一、只读诊断   | 电脑体检、启动项、端口占用、大文件扫描、磁盘健康                                | ✅ 已完成 |
| 二、基础完善   | 硬件信息快照、进程列表、软件卸载列表、重复文件、目录占用树图、文件哈希、Hosts 查看、**回滚引擎骨架** | 进行中   |
| 三、高级与差异化 | SFC/DISM、电池健康、蓝屏简化分析、DNS 切换、报告导出、定时体检、前后对比              | 待排期   |

### 15.7 产品红线

**六不**：不弹广告、不强制安装其他软件、不后台偷偷运行、不未经允许改注册表、
不盲目关闭 Windows 服务、不展示虚假的性能提升百分比。

**三原则**：**安全 · 透明 · 可还原**——每个动作都要能说清"改了什么、怎么验证、怎么撤回"。

如后续商业化：高级硬件监控、自动诊断、优化方案、定时维护可作收费项；
基础清理、网络诊断、系统信息保持免费。

### 15.8 依赖准入（约束松绑后新增）

> 背景：原方案把「零依赖」当硬约束，现允许引入第三方开源库（见第二章第 5 条）。
> 为避免从「一个库都不用」滑成「什么库都装」，先定规则，再谈候选库。

**准入四条（全部满足才可引入）**

1. **许可证白名单**：MIT / Apache-2.0 / BSD / ISC / zlib / Public Domain；
   LGPL 仅允许动态链接（Qt 本身即 LGPLv3 动态链接）；**GPL / AGPL 一律不用**（含 smartmontools、BleachBit 代码）。
2. **体积与形式**：单依赖 ≤ 5 MB，优先源码内嵌或静态链接；不引入需要独立安装器的运行时（.NET / JRE / Python 等）。
3. **可维护**：最近 12 个月有提交，或有明确的上游团队；一次性个人项目不用。
4. **可审计**：新增依赖必须登记到本文（名称 / 版本 / 许可证 / 用途 / 体积 / 引入日期），并在「关于」页列出。

**候选库（用到时才引入，不预装）**

| 库 | 许可证 | 潜在用途 | 结论 |
|---|---|---|---|
| SQLite（amalgamation） | Public Domain | 回滚引擎的操作记录与索引 | 候选：15.5 落地时再引入 |
| QXlsx | MIT | 导出 xlsx 报表 | 可选：HTML/CSV 够用就不引入 |
| minizip-ng / QuaZip | zlib / LGPL（动态） | 日志与报告打包 | 可选 |
| WIL（Windows Implementation Library） | MIT | Win32/COM 的 RAII 封装 | 可选：COM 调用变多时引入 |
| 思源黑体子集 / Noto Sans | SIL OFL | 统一字体与图标字形 | 可选 |
| NVML（NVIDIA SDK） | 闭源 | GPU 温度与利用率 | **不引入**（违反第 2 条，暂不承诺 GPU 温度） |
| LibreHardwareMonitorLib | MPL-2.0（.NET） | 全硬件传感器 | **不引入**（违反第 2 条） |
| smartmontools | GPL-2.0 | 直接读 SMART | **不引入**（违反第 1 条），继续用 `Get-StorageReliabilityCounter` |

**仍然优先系统组件**：WMI、PDH、ETW、Win32 API 与 PowerShell 已覆盖绝大多数读取需求；
第三方库只在「系统组件确实做不到」时才用——这是对第二章第 5 条的具体约束。
