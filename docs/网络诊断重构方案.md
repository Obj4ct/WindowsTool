# WindowsTool 网络检测重构方案

> 状态：**待评审**　　作者：智瞳　　日期：2026-10-30
> 目标：把「ping 一下看通不通」升级为「分层定位 + 精准修复」

> **2026-10-30 更新**：功能裁剪与弹窗文案规范化已落地（见 5.2），
> 网络检测逻辑重构（阶段 1–4）尚未实施。

## 一、现状诊断

### 1.1 当前的检测逻辑

```
点击「自动检测并修复」
    ↓
ping www.baidu.com                         ← 唯一探测点
    ↓
  找不到主机 ──→ ping www.baidu.com（第二次）
                      ↓
                  nslookup baidu.com
                      ↓
                  DNS 失败 ──→ fixDNS.bat → 问用户"能上网了吗"
                      ↓
                  通过 → "网络连接正常"
```

### 1.2 实测发现的问题

| # | 问题 | 实测证据 | 严重度 |
|---|---|---|---|
| 1 | **单点探测，结论必然片面** | 本机 5 个网卡同时 Up（以太网 / WLAN / VMware VMnet1 / VMnet8 / xray_tun）。`Test-NetConnection` 实测流量实际走 **`xray_tun`**，而 ping 走的是同一路径——但用户可能以为在用 WLAN | 🔴 高 |
| 2 | **DNS 检测靠解析本地化文本** | `netcheck.h` 里硬编码 `"找不到主机"` / `"Non-existent domain"` 等 7 个关键词。换个系统语言就失效 | 🔴 高 |
| 3 | **DNS 检测绕过真实路径** | `nslookup` 直接问 DNS 服务器，而浏览器实际走的是「代理 → VPN 隧道 → DNS」。三者可能给出完全不同的答案 | 🟠 中 |
| 4 | **代理因素完全未考虑** | 本机 `ProxyEnable=1, ProxyServer=127.0.0.1:10808`。作者自己在提示语里写过"确保在电脑设置中关闭了代理"，但程序**从不检测代理** | 🟠 中 |
| 5 | **`fixDNS.bat` 在中文系统上静默失效** | `netsh interface show interface` 中文系统输出表头是「管理员状态/状态/类型/接口名称」，脚本里的 `findstr /c:"Admin State"` **永远匹配不到** | 🔴 高 |
| 6 | **`fixDNS.bat` 会破坏用户配置** | 它把**所有**网卡重置为 DHCP：会抹掉手工设的静态 IP；会把 VPN 虚拟网卡（xray_tun / Wintun）也去设 DHCP——这类适配器压根不适用 | 🔴 高 |
| 7 | **"修复"无法验证** | 修复后靠弹窗问用户"是否可以上网"，是主观判断，且没有复检 | 🟡 中 |
| 8 | **结果只有纯文本** | 诊断结论混在日志流里，看不出"哪一层出问题" | 🟡 中 |

### 1.3 一个典型的误判场景

> 用户接了 VPN（或公司配了代理），DNS 走的是代理的 DNS。
> 本机 `nslookup` 查的是网卡上配的 `192.168.3.1`（WLAN 的 DNS）→ 成功 → 程序说"网络正常"。
> 但浏览器访问走代理，代理挂了 → 用户实际上打不开网页。
> **程序给的是假绿灯。**

## 二、目标

1. **分层定位**：明确回答"断在哪一层"，而不是"网络有问题"
2. **结论可靠**：不依赖系统语言、不依赖某个外部命令的输出格式
3. **修复精准**：按诊断结论选择动作，不做全局破坏性操作
4. **结果可读**：结构化展示 + 可复制分享
5. **零新增依赖**：不引入第三方库，继续只用 Qt + 系统自带组件

## 三、方案架构

### 3.1 总体结构

```
┌─────────────────────────────────────────────────────────┐
│  MainWindow                                               │
│  ┌───────────────────┐  ┌─────────────────────────────┐ │
│  │ NetDiag（新增）    │  │ ProcessRunner（现有）        │ │
│  │ 分层探测编排       │  │ 跑 bat / PowerShell 脚本     │ │
│  └─────────┬─────────┘  └──────────────┬──────────────┘ │
│            │                           │                │
│   ┌────────┴────────┐         ┌────────┴────────┐       │
│   │ QNetworkAccess   │         │ netdiag.ps1     │       │
│   │ Manager（Qt 内）  │         │ 本机状态快照     │       │
│   │ · DNS 探测        │         │ → JSON          │       │
│   │ · HTTP 端到端     │         │ （网卡/路由/代理）│       │
│   │ · 原始 UDP DNS   │         └─────────────────┘       │
│   └──────────────────┘                                    │
└─────────────────────────────────────────────────────────┘
```

### 3.2 关键决策：PowerShell 只做「读状态」，探测全部在 Qt 内

| 事项 | 放在哪 | 理由 |
|---|---|---|
| 网卡 / IP / 网关 / DNS / 默认路由 / 代理 | PowerShell（输出 JSON） | 这是 OS 内部状态，Qt 没有 API 能拿；`Get-NetAdapter` 等 cmdlet **输出与系统语言无关** |
| DNS 能否解析 | Qt 内自己发 UDP DNS 查询 | 绕开 `nslookup`/`Resolve-DnsName` 的文本输出，100% 可控、可测延迟、可指定服务器 |
| HTTP 端到端能否访问 | Qt 内 `QNetworkAccessManager` | 直接用浏览器的网络栈（含系统代理），最接近用户真实体验 |

**为什么不全程用 PowerShell？** 每起一个 powershell 进程约 300–800ms，多项检测累积到 3–5 秒，界面明显卡顿。折中：**一次调用拿全部本机状态（JSON），其余在 Qt 内快速完成**。

## 四、分层诊断模型（核心）

从下往上逐层检查，**报告第一个失败的层**。

```
┌──────────────────────────────────────────────────────────┐
│ L7 应用层   浏览器实际访问（走系统代理 + WinINET）           │  ← 最贴近用户体验
├──────────────────────────────────────────────────────────┤
│ L6 代理层   系统代理 / PAC / WinHTTP 代理 是否存在且可达      │  ← 常见坑
├──────────────────────────────────────────────────────────┤
│ L5 HTTP 层   HTTPS 请求能否拿到响应（含 TLS 握手）           │
├──────────────────────────────────────────────────────────┤
│ L4 TCP 层    到目标 IP:443 能否建立连接                      │  ← 防火墙/墙在这里
├──────────────────────────────────────────────────────────┤
│ L3 DNS 层    域名能否解析成 IP                              │  ← 最高频故障点
├──────────────────────────────────────────────────────────┤
│ L2 路由层    到目标 IP 有无路由，实际走哪个网卡                │
├──────────────────────────────────────────────────────────┤
│ L1 链路层    目标网卡是否 Up、有无有效 IP、有无默认网关        │  ← 拔网线/无WiFi
└──────────────────────────────────────────────────────────┘
```

### 4.1 各层判定与输出

| 层 | 检查方式 | 失败结论 | 建议动作 |
|---|---|---|---|
| L1 | JSON 里网卡状态 / IP / 网关 | `未连接` / `IP 配置异常` | 检查网线、WiFi、DHCP |
| L2 | 默认路由 + 路由表匹配目标 IP | `路由缺失` | 检查静态路由/VPN 路由 |
| L3 | 自发 UDP DNS 查询 | `DNS 解析失败` | 换 DNS / 刷 DNS 缓存 |
| L4 | TCP connect | `连接被阻断` | 检查防火墙、代理软件 |
| L5 | HTTPS 请求 | `HTTP 异常` | 检查证书、代理认证 |
| L6 | 代理注册表 + 连通性 | `代理不可用` | 关闭/更换代理 |
| L7 | 用系统代理栈发请求 | `浏览器也无法访问` | 综合判定 |

### 4.2 判定结果的数据结构

```cpp
enum class Layer { Link, Route, Dns, Tcp, Http, Proxy, App };

struct CheckItem {
    Layer      layer;
    QString    name;        // "DNS 解析"
    Status     status;      // Pass / Fail / Warn / Skip
    QString    detail;      // "223.5.5.5 响应 23ms"
    int        elapsedMs = -1;
};

struct DiagResult {
    QVector<CheckItem> items;
    Layer    firstFailed = Layer::App;   // 首个失败层
    QString  summary;                     // 一句话结论
    QString  suggestion;                  // 针对性建议
};
```

### 5.2.2 建议裁剪（待确认，未实施）

| 功能 | 建议 | 理由 |
|---|---|---|
| **垃圾清理** | **建议移除**，或改为「打开系统临时文件清理面板」 | ① 收益极小：现代 Windows 的临时文件本就由系统按需清理 ② 代价高：需提权弹 UAC、弹黑窗口 ③ 有风险：自己写删除逻辑，一旦路径判断失误就是误删 ④ 已有更好的：Windows 自带「设置 → 系统 → 存储 → 临时文件」，覆盖面更全更安全。<br>**替代方案**：改成一行命令调起系统清理面板，用户在原生界面里勾选要删什么——我们只负责"打开入口"，不做删除动作。 |
| **重置 WinSock** | **保留**，但明确标注代价 | 有真实场景（安全软件残留导致协议栈异常），无系统原生替代。但需重启才生效，必须在确认弹窗里说清楚。 |

### 5.2.3 弹窗文案规范化（已落地）

原实现的弹窗大量使用口语与情绪化表达（"疑问"、"别开玩笑"、"555，你开心就好了"），
在故障场景下会让用户觉得"这软件不靠谱"。规范化原则：

1. **标题 = 动作或结果**，不用情绪词 —— "刷新网络配置" 而非 "提示"
2. **正文 = 发生了什么 → 可能原因 → 建议动作**，三段式
3. **涉及系统改动必须前置警示** —— 说明影响范围、是否可逆、是否需要重启
4. **错误信息要具体** —— 指明缺哪个文件、完整路径，而非"找不到脚本文件"
5. **按钮文案描述动作** —— "可以正常访问" 而非 "可以"

对比示例：

| 场景 | 改前 | 改后 |
|---|---|---|
| 网络测试失败 | 标题「连接错误」<br>"网络连接出现问题，请检查是否连接网络（建议多检测几次）。如果已经连接，建议使用自动检测来检查问题" | 标题「连接超时」<br>"在规定时间内未收到目标主机的响应。\n\n可能原因：网络尚未连接、目标站点不可达，或存在代理/防火墙拦截。\n\n建议使用「自动检测并修复」定位具体故障环节。" |
| 修复后验证 | 标题「疑问」<br>"是否可以上网？" | 标题「验证修复结果」<br>"网络配置已重置。请问当前是否可以正常访问网页？" |
| 修复仍失败 | 标题「开发者的话」<br>"软件为第一个版本，难免会有问题，请点击右上角「关于」来联系作者" | 标题「问题仍未解决」<br>"网络配置已重置，但访问仍不正常。\n\n可能是运营商侧故障、代理配置异常，或被安全软件拦截。\n\n可通过右上角「关于」获取联系方式以获取进一步支持。" |
| 脚本缺失 | 标题「错误」<br>"找不到脚本文件 fixDNS.bat" | 标题「缺少脚本文件」<br>"未找到所需的脚本文件 fixDNS.bat。\n\n请确认程序目录下的 bat 文件夹完整，或重新获取程序。" |
| 重置 WinSock 确认 | 标题「警告！」<br>一长串口语化描述 | 标题「重置 Winsock」<br>"此操作将重新初始化 Winsock 套接字目录…\n\n注意：重置后部分网络性能可能下降，且需要重启计算机才能完全生效。\n\n是否继续？" |

> 注：文案规范化属于**表面改动**，真正让结论可信的是第五节的 F1 分层诊断——
> 专业文案的配得上"专业"二字，前提是诊断结论本身准确。

| 风险 | 影响 | 应对 |
|---|---|---|
| **修复动作会改系统网络配置** | 可能短暂断网，或影响静态 IP 用户 | 每次修改前**自动备份**原配置，提供回滚；只对**当前默认路由网卡**操作；物理网卡与虚拟网卡分开处理 |
| PowerShell 被策略禁用/缺失 | 本机状态拿不到 | 降级到解析 `ipconfig /all`（有本地化风险），或直接跳过对应检查项并明示 |
| Win7 / 旧版 PowerShell | `Get-NetAdapter` 等 cmdlet 可能不存在 | 脚本里做版本探测，不可用则用 `netsh` 兜底 |
| 一次 PowerShell 调用 300–800ms | 界面短暂停顿 | 异步执行 + 状态条提示；**所有本机状态一次拿完**，不做多次调用 |
| UDP DNS 被企业防火墙拦截 | F2 测不出延迟 | 探测超时≠DNS 故障，结合 L4/L5 结论综合判断，不单独下结论 |
| 内置公共 DNS 属于"改动用户环境" | 用户可能不希望 | 默认**只测速不自动切换**；切换需显式点击 + 二次确认 |
| 诊断逻辑复杂度上升 | 维护成本 | 分层模型用数据驱动（`CheckItem` 数组），每层独立可测；引擎不碰 UI |

## 九、需要你拍板的几个点

> 已定事项：① 公共 DNS 切换——做，默认只测速，切换需二次确认；
> ② `netdiag.ps1` 放 `ps1/` 目录；③ 快捷键与截图功能已裁剪（见 5.2.1）。

1. **诊断结果要不要落盘保存历史？**
   涉及写文件到用户目录，可以只保留在内存里（本次退出即清）。

2. **网络页 UI 是"卡片列表"还是"保持现在的磁贴 + 展开详情"？**
   前者信息密度高、后者改动小。我倾向**磁贴保留、点击后展开分层结果面板**。

3. **「垃圾清理」要不要按建议改成「打开系统清理面板」？**
   见 5.2.2。改成调起 Windows 原生清理界面，我们不做删除动作——更安全也更省事。

4. **系统页留白要不要用 F15 填上？**
   现在系统页只有两个磁贴，下方大片空白。可以加「开机启动项管理」「服务管理」等。

## 十、不做什么（避免范围膨胀）

- ❌ 不做流量抓包 / Wireshark 替代品
- ❌ 不做网速测速的严谨实现（只做延迟/丢包近似）
- ❌ 不做路由表编辑器（危险且小众）
- ❌ 不引入任何第三方库（保持零依赖）
- ❌ 不改动 `bat/` 现有脚本的 GBK 编码约定
- ❌ **不做与"修复常见电脑问题"无关的功能**（快捷键速查、截图教学等已裁剪）
